# How to Use the Program

This guide explains how to move through the curriculum, study each module, use problem sets and computational labs, and decide when work is complete. The intended pace is **3–5 hours per week**. Consistency and retained understanding matter more than speed.

## 1. Follow the sequence, not the repository file order

The repository contains courses, reference materials, research casebooks, and computational projects. They serve different purposes:

- **Courses** provide an ordered learning sequence with prerequisites, outcomes, assessments, and completion evidence.
- **Problem sets** test whether you can derive and apply the material without relying on worked examples.
- **Computational labs** turn concepts into reproducible models and code.
- **Casebooks** organize primary sources and institutional facts around a real policy or engineering question.
- **Research projects** combine methods to answer a focused question. They are not automatically equivalent to completed courses.

Use the [curriculum map](course-map.md) to identify the current course and its prerequisites. Do not treat every repository folder as a required assignment.

## 2. Recommended learning path

1. **Orient and diagnose.** Read the [program overview](program-overview.md), [prerequisite diagnostic](prerequisites.md), and [academic standards](../ACADEMIC_STANDARDS.md). Complete only the prerequisite remediation indicated by the diagnostic.
2. **Build Year 1 foundations.** Work through power systems, energy economics, quantitative methods, and then electricity markets/regulation. Quantitative methods can overlap with the other courses once the relevant mathematics and basic data skills are comfortable.
3. **Complete the Year 1 integration project.** Choose a narrow question, assemble public evidence, produce an analysis, and write a short policy or technical brief.
4. **Enter Year 2 selectively.** Use the advanced mathematics sequence to strengthen mathematical maturity and take econometrics in a sequence that fits the workload. Do not attempt every Year 2 topic at once.
5. **Specialize through research.** Select a technical or policy concentration only after identifying a question, data or model feasibility, and a credible method.

The program is independent study. Its four-year roadmap is a planning horizon, not a guarantee of mastery or a degree-equivalent credential.

## 3. A repeatable weekly study cycle

A typical four-hour week can be organized as follows. Shift the balance when a problem set or project requires more time.

| Activity | Typical time | What to produce |
|---|---:|---|
| Textbook or lecture | 60–90 min | Annotated notes and questions |
| Primary source or research paper | 45–60 min | Source note: claim, evidence, limitations |
| Problem set or computational work | 75–105 min | Derivation, code, calculations, or tests |
| Retrieval and synthesis | 30–45 min | Short explanation from memory and research-log entry |

A productive session should leave an artifact: a solved derivation, tested code change, source note, diagram, or concise written explanation. Passive reading alone is not completion evidence.

## 4. How to study a course

For each course:

1. Read the purpose, prerequisites, learning outcomes, and weekly sequence before starting.
2. Check the prerequisites. Remediate specific gaps rather than restarting entire undergraduate subjects.
3. Follow the weekly sequence, but slow down when a derivation or model is not yet understood.
4. Attempt each problem set before opening its worked solution.
5. Complete computational labs from a clean environment. Re-run the tests and explain what the model omits.
6. Write the required memo or synthesis in your own words, citing the evidence actually consulted.
7. Review the rubric and record evidence in the progress trackers.

**Do not equate exposure with mastery.** Being able to recognize a formula is weaker than deriving it, selecting when it applies, checking its assumptions, and explaining its limitations.

## 5. How to use worked solutions

Worked solutions are for feedback, not a substitute for attempting the assignment.

- First attempt the problem without looking at the solution.
- Mark uncertain steps and assumptions while working.
- Compare the solution only after producing a complete attempt.
- Classify each discrepancy: concept error, algebra error, unit error, coding error, unsupported assumption, or interpretation error.
- Correct the work and write a brief explanation of the correction.
- Revisit the problem later without notes.

A problem set is not complete merely because its solution file has been read. Preserve the original attempt and corrected version where useful.

## 6. How to use computational labs

Each lab should identify its objective, model, inputs, run instructions, expected outputs, tests, assumptions, and limitations.

A reliable workflow is:

1. Read the lab README and inspect the input schema before running code.
2. Create or activate the documented Python environment.
3. Install the lab's listed dependencies.
4. Run the example and automated tests.
5. Trace at least one important result back to the equations and input data.
6. Change one parameter or scenario and explain the effect.
7. Record model limitations and whether the result is synthetic, observational, or externally sourced.

A passing test suite verifies specified software behavior. It does not establish that a model is empirically valid, physically complete, or suitable for operational decisions.

## 7. Evidence and completion

Use the [academic standards](../ACADEMIC_STANDARDS.md) and the progress trackers. Record actual study time and link completed work. A course completion claim should be supported by:

- Demonstrated learning outcomes.
- Attempted and corrected assessments.
- Reproducible computational or empirical work.
- A written analytical deliverable.
- A self-assessment of remaining weaknesses.

The internal rubric is a self-audit instrument, not an external grade or independent examination.

## 8. Research integrity and data boundaries

Use public, licensed, and appropriately documented information. Preserve source URLs, access dates, versions, transformations, exclusions, and data dictionaries. Distinguish descriptive evidence from causal evidence. State uncertainty and model limitations.

Do not place confidential employer information, customer information, nonpublic grid data, credentials, or restricted datasets in this repository. A public-data project should not imply access to or representativeness of confidential operational records.
